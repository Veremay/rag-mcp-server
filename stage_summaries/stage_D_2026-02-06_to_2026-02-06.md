## 阶段目标

- 在线查询链路跑通：Dense + Sparse 召回，RRF 融合，可选 Rerank，并返回 Top-K chunks（含可定位的元信息），同时具备稳定回退策略。

## 完成内容清单

- D1 QueryProcessor（关键词提取 + filters）：实现 query 预处理与元数据过滤解析。
- D2 DenseRetriever：对 query 做 embedding，并调用 VectorStore.query 返回 dense 候选与分数。
- D3 SparseRetriever（BM25）：基于本地 BM25 索引做关键词召回。
- D4 Fusion（RRF）：实现 RRF 融合 dense/sparse 排名，输出统一候选排序。
- D5 HybridSearch：编排 dense + sparse + fusion，输出可用于下游的候选集合。
- D6 Reranker（含 fallback）：接入 reranker 后端，失败/超时回退 fusion 结果并携带标记。
- D7 脚本入口 query.py：提供 CLI 查询入口，支持 verbose 分阶段输出，便于本地调试与验证。

## 关键实现点

- QueryProcessor：将自然语言 query 拆分为 keywords，并解析如 `collection:xxx` 的过滤条件，作为 dense/sparse 的统一输入。
- DenseRetriever：
  - embedding provider 可插拔（openai/local/ollama），vector store 可插拔（chroma/jsonl）。
  - 在 CLI 中补充了“缺少依赖/配置”的提前失败与清晰提示（例如缺少 chromadb、缺少 OpenAI key）。
  - 对 OpenAI embedding 超时/网络失败场景，CLI 增加自动回退到 local embedding（仅用于链路调试，相关性会下降）。
- SparseRetriever：统一从 `data/db/bm25/` 的索引读取并检索，collection 解析优先级为 CLI 参数 > filters > settings 默认。
- Fusion（RRF）：将 dense/sparse 的排序位置转为可融合的分数并输出稳定排序，保证 deterministic。
- Reranker：将候选列表交给后端（none/cross_encoder/llm），异常时回退 fusion 并显式标记 fallback。
- query.py：
  - 支持 `--query/--top-k/--collection/--verbose/--no-rerank/--config`
  - verbose 下打印 Dense / Sparse / Fusion / Rerank 各阶段中间结果，便于定位召回与排序问题。

## 面试问题与答案（阶段 D）

> Updated: 2026-02-06 12:00

1. 你能从端到端描述一次在线查询的完整链路吗？各阶段输入/输出分别是什么？
   - 参考答案：本阶段链路以 CLI（`scripts/query.py`）为入口，核心数据流是：QueryProcessor 产出结构化 query（keywords）与 filters → HybridSearch 同时执行 DenseRetriever（Embedding + VectorStore.query）与 SparseRetriever（BM25）得到两组候选 → Fusion（RRF）做稳定融合排序 → 可选 Reranker 对 Top-M 候选重排 → 输出 Top-K chunks（含可定位的元信息）并支持 verbose 分阶段打印。这样拆分的动机是将“语义编码、关键词检索、融合排序、重排”职责隔离，便于替换后端、做降级与单测。资源侧，Dense 会触发 embedding（可能网络/费用），Sparse 主要是本地 CPU/内存与索引 IO，Reranker 额外引入时延与算力。

2. 为什么要做 Hybrid Search（Dense + Sparse）而不是只用其中一种？
   - 参考答案：Dense 擅长语义相近但字面不匹配的召回，Sparse（BM25）对精确关键词、专有名词、ID/版本号更稳定；二者互补能显著提升召回鲁棒性。工程上，Hybrid 还能在某一侧不可用时（例如 embedding 超时、外部依赖缺失）提供降级空间：至少保留另一侧结果，再用融合策略输出可用 Top-K。资源侧，Dense 受限于 embedding 成本与延迟，Sparse 受限于索引大小与 CPU，Hybrid 需要额外融合开销但可控。

3. BM25 的基本原理是什么？为什么它适合作为 Sparse Retriever？
   - 参考答案：BM25 基于 TF（词频）与 IDF（逆文档频率）以及文档长度归一化，对包含查询关键词的文档给出相关性评分；它不依赖外部模型、实现简单、可解释性强、对“关键词必须出现”的场景非常可靠。本阶段将 BM25 索引统一落在 `data/db/bm25/`，便于离线构建与在线读取。资源侧，索引文件会占用磁盘与一定内存映射/加载开销，查询耗时主要在倒排表扫描与打分。

4. RRF（Reciprocal Rank Fusion）是什么？为什么选择它做融合，而不是直接加权相加分数？
   - 参考答案：RRF 只依赖各检索器的“排序名次”而非原始分数尺度，公式典型为对同一候选的融合分数累加 `1 / (k + rank)`；它能天然消除 Dense/Sparse 分数分布不一致带来的校准问题，并且对各检索器的长尾噪声更稳健，适合作为通用融合基线。本阶段强调 deterministic 输出，RRF 更容易稳定复现与测试。可运行示例：

```python
# Python >=3.10
from __future__ import annotations

def rrf_fuse(rank_lists: list[list[str]], k: int = 60) -> list[tuple[str, float]]:
    scores: dict[str, float] = {}
    for ranks in rank_lists:
        for idx, doc_id in enumerate(ranks, start=1):
            scores[doc_id] = scores.get(doc_id, 0.0) + 1.0 / (k + idx)
    return sorted(scores.items(), key=lambda x: x[1], reverse=True)

print(rrf_fuse([["a", "b", "c"], ["b", "c", "d"]], k=60)[:3])
```

5. 你会如何选择 Fusion 之前的 Top-M、最终输出的 Top-K？它们对效果/成本有什么影响？
   - 参考答案：Top-M 决定进入 Reranker 或后续处理的候选规模，M 越大潜在召回越高但成本越高（尤其是 cross-encoder/LLM rerank 会近似线性增加时间/费用）；Top-K 是最终返回给用户的数量，K 越大更“全”但会增加下游上下文拼接与展示成本。实践上一般先固定 K（用户体验驱动），再从可接受的 rerank 时延/成本倒推 M，并通过离线评估或线上 AB 调整。资源提示：当 reranker 后端为 LLM 时，M 是最主要的费用杠杆。

6. QueryProcessor 为什么要做“关键词提取 + filters 解析”？filters 统一输入能带来什么工程收益？
   - 参考答案：关键词提取让 Sparse Retriever 有稳定输入（否则用整句会引入大量噪声 token），filters 解析将类似 `collection:xxx` 的条件从 query 中抽离，避免检索器自行解析导致逻辑分叉。统一输入的收益是：Dense/Sparse 共享同一套过滤条件，减少“召回集合不一致”的隐性 bug；也便于在 CLI 层给出清晰优先级（本阶段明确 collection 解析优先级：CLI 参数 > filters > settings 默认），提升可预测性。

7. embedding provider（openai/local/ollama）可插拔的设计价值是什么？落地时最容易踩的坑有哪些？
   - 参考答案：可插拔让同一条查询链路能在不同环境运行：本地开发可用 local embedding 做链路调试，生产环境可用 OpenAI 或 Ollama 追求效果/隐私；同时便于在成本、延迟、隐私合规之间做切换。常见坑：不同 provider 的维度/归一化不一致导致向量检索质量波动；网络超时与限流带来不稳定；以及 SDK 版本差异（本项目 `openai>=1.0.0`，调用方式与旧版不同）。资源提示：远程 embedding 的主要成本是网络 RTT + 计费 token，需配合超时与重试策略。

8. vector store 后端（chroma/jsonl）可插拔时，接口契约应该怎么定，才能避免上层被“泄漏实现细节”绑死？
   - 参考答案：核心是用最小稳定接口描述能力，例如：`upsert(docs, embeddings, metadata)`、`query(vector, top_k, filters)`、返回结构包含 `id/text/metadata/score` 等通用字段，避免暴露 Chroma 特有的 collection API 或 JSONL 特有的文件布局。上层只依赖契约，具体后端通过配置切换（本阶段总结里明确 `vector_store.backend` 可切换）。兼容点：`chromadb>=0.4.0` 才能满足当前依赖；资源提示：Chroma 会引入额外依赖与本地存储管理开销，JSONL 更轻但适合小规模与调试场景。

9. CLI 层“提前失败 + 清晰提示”相比让异常堆栈直接暴露，有什么好处？你会如何设计错误码与提示内容？
   - 参考答案：提前失败把“可预期的环境问题”（缺少 chromadb、缺少 OpenAI key、配置错误）在入口处转成可执行的行动建议，减少排障时间，也避免用户误以为是业务逻辑 bug。错误码/退出码应能区分配置错误、依赖缺失、网络问题等；提示内容要给出最短路径（例如安装依赖或切换 backend/provider）。资源提示：对网络超时类错误要提示可能的网络/代理问题，并建议使用 local embedding 做离线验证。

10. OpenAI embedding 超时/网络失败时，为什么选择“自动回退到 local embedding（仅用于链路调试）”？这种策略的风险是什么？
   - 参考答案：本阶段目标是“查询链路跑通并可调试”，因此在外部服务不稳定时自动回退可以保证功能可用性与验证效率；但风险是检索相关性会下降，且结果分布与生产环境差异大，不能用于效果评估或线上服务承诺。因此需要在输出/verbose 中明确标识回退发生，并在文档/面试回答中强调“仅用于调试”。可运行示例（展示“失败即回退”的控制流）：

```python
# Python >=3.10
from __future__ import annotations

def embed_with_fallback(text: str) -> tuple[str, list[float]]:
    try:
        raise TimeoutError("openai timeout")
    except Exception:
        return ("local", [0.1, 0.2, 0.3])

provider, vec = embed_with_fallback("hello")
print(provider, vec)
```

11. Reranker 在这条链路中的定位是什么？什么时候应该关掉 rerank？
   - 参考答案：Reranker 是“精排”，用于在召回集合已相对正确时提升 Top-K 排序质量，特别适合 Dense/Sparse 都能召回但排序不稳定的场景。应在这些情况下关闭：对时延敏感、算力/费用受限、候选量较大且 reranker 质量不稳定、或仅做链路连通性验证（本阶段 CLI 支持 `--no-rerank`）。资源提示：cross-encoder/LLM rerank 成本通常与候选数 M 成正比，是链路中最重的一环。

12. 你如何设计“Reranker 失败/超时 → fallback fusion 结果”的降级策略，确保对用户体验最友好？
   - 参考答案：策略关键点是：保持返回结构与字段稳定（仍返回 Top-K chunks），同时显式标记发生了 fallback，便于调用方在 UI/日志中提示“结果未 rerank”。超时阈值应保守设置，避免长尾请求拖垮整体；并在 fallback 后继续返回融合结果而不是报错，这样“可用性优先”。资源提示：需要限制并发与超时，避免线程/连接堆积。

13. 你会如何保证融合与返回结果的 deterministic（可复现）？为什么这在工程上重要？
   - 参考答案：本阶段强调 deterministic：RRF 只依赖名次，给定同样输入排序应一致；在同分场景要有稳定 tie-break（例如按 doc_id），同时避免使用不可控随机源。可复现性对单测、回归、线上问题复盘很关键，能降低“同一 query 结果飘”的排障成本。资源提示：deterministic 往往与并行化存在张力，需要在并发与稳定性之间权衡。

14. verbose 分阶段输出应该包含哪些信息？哪些信息绝对不应该输出？
   - 参考答案：应包含每阶段候选的 Top-N 摘要（id、score、关键 metadata、命中关键词等）以及是否启用 rerank、是否发生 fallback，便于定位“召回缺失/融合异常/精排失败”。绝不输出：API key、完整敏感文本、用户隐私字段，或可能导致数据泄漏的原始索引内容。兼容点：本项目基于 Python CLI 输出，需注意跨平台编码与 stderr/stdout 分流。资源提示：verbose 会显著增大 IO 与日志量，线上默认应关闭。

15. 你会如何为 QueryProcessor、DenseRetriever、SparseRetriever、Fusion、Reranker 设计测试？单测与集成测试各验证什么？
   - 参考答案：单测验证“模块契约与边界”：QueryProcessor 的关键词与 filters 解析、DenseRetriever 在 provider mock 下的输入输出、SparseRetriever 的 BM25 查询行为、Fusion 的 RRF 排名稳定性、Reranker 的超时/异常 fallback 行为；集成测试验证“链路编排与数据流正确性”（HybridSearch 串起 dense+sparse+fusion，并能在某一路失败时仍返回结果）。本阶段已经给出核心回归命令（`pytest -q ...`）。资源提示：集成测试应尽量使用小数据/假 embedding，避免引入外部网络与费用。

16. 在 HybridSearch 中你会考虑并行执行 Dense 与 Sparse 吗？并行带来的收益与风险分别是什么？
   - 参考答案：并行的收益是降低端到端 P95 时延（两路取 max 而不是 sum），尤其当 embedding 或 BM25 其中一路较慢时更明显；风险是并发带来的资源竞争（CPU/IO）、以及错误处理复杂度上升（需要聚合两路错误并做合理降级）。工程上可先串行保证正确性与可测性，再在明确的超时/并发上限下引入并行。资源提示：并行需要设置线程池/协程上限，避免在高并发下把外部 embedding 服务打爆。

17. 在“依赖缺失（如 chromadb 未安装）”与“运行期失败（如 OpenAI 超时）”两类问题上，错误处理策略应该有什么不同？
   - 参考答案：依赖缺失是确定性配置/环境问题，应该在入口处尽早发现并以可行动提示终止（或指导切换 backend）；运行期失败是概率性问题，应通过超时、重试、熔断与降级（例如回退 local embedding 或回退 fusion）来提高可用性。两者都要保证不会影响其他业务流程：本阶段的处理聚焦在 CLI 可运行性与提示友好，不改变核心检索逻辑契约。

18. 如果要把当前 CLI 查询链路接入到 MCP Tool（stdio transport / JSON-RPC 2.0），你会怎么设计输入输出协议？
   - 参考答案：输入应包含 `query`、`top_k`、`collection`、`filters`、`rerank` 开关、`verbose`（或 debug level）等；输出应标准化为 `results`（含 chunk_id/text/metadata/score）并携带 `diagnostics`（例如 dense/sparse 命中数量、是否 fallback、耗时统计）。协议层应与内部模块解耦：MCP 只做参数校验与调用编排，核心检索仍由 QueryProcessor/HybridSearch 等模块承担。兼容点：JSON-RPC 2.0 对错误对象结构有要求，需把内部异常映射为稳定错误码。资源提示：协议输出需限制长度，避免一次返回过大文本导致传输与前端渲染压力。
