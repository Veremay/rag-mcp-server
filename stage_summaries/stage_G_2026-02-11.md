# 阶段 G 总结：可视化管理平台 (Dashboard)

> Generated: 2026-02-11
> Spec Reference: DEV_SPEC.md Section G

## 1. 阶段目标
构建基于 Streamlit 的可视化管理平台，提供以下核心能力：
- **系统总览**：展示系统状态、组件配置及关键指标。
- **知识库管理**：浏览/搜索已摄取的文档块，管理文档元数据。
- **摄取管理**：触发摄取任务，查看摄取进度。
- **可观测性**：可视化 Ingestion 和 Query 的链路追踪数据。

## 面试问题与答案（阶段 G）

> Updated: 2026-02-11 10:00

1. **Dashboard 的整体架构是如何设计的？为什么要引入 Services 层？**
   - **参考答案**：Dashboard 基于 Streamlit 框架构建，采用了“UI - Services - Core”的分层架构。`app.py` 负责路由分发（使用 `st.navigation`），`pages/` 目录负责具体的 UI 渲染。为了解耦 UI 展示逻辑与底层数据获取逻辑，引入了 `services/` 层（如 `TraceService`, `ConfigService`）。这样设计的好处是：UI 代码更专注于交互展示，后端逻辑（如日志解析、数据库连接）被封装在 Service 中，便于测试和复用，同时也规避了 Streamlit 脚本重运行机制下可能导致的对象重复创建问题（配合 `st.cache_resource`）。

2. **Streamlit 的运行机制是“脚本从头执行”，你是如何管理全局状态（如配置加载、Service 单例）的？**
   - **参考答案**：利用 Streamlit 提供的 `st.cache_resource` 装饰器来实现单例模式。例如 `AppContext` 或 `DocumentManager` 的初始化被标记为缓存资源，确保在应用的生命周期内只被创建一次，不会因为用户的每一次点击交互而重新连接数据库或重新加载配置文件。对于页面间的临时状态，则使用 `st.session_state` 进行传递。

3. **请介绍一下 `DocumentManager` 的作用。为什么需要这样一个统一的管理器？**
   - **参考答案**：`DocumentManager` 是为了解决“多存储一致性”问题而设计的。我们的 RAG 系统同时使用了 Chroma（向量存储）、BM25（倒排索引）和 ImageStorage（图片存储）。如果没有统一管理器，删除或更新文档时容易出现漏删（例如删除了向量但留下了图片）。`DocumentManager` 封装了这些底层存储的操作接口，对外提供统一的 CRUD 方法，确保对文档的操作能原子性地（逻辑上）应用到所有相关存储后端。

4. **在可视化全链路追踪（Tracing）时，数据源来自哪里？为什么选择这种方式？**
   - **参考答案**：追踪数据源自本地的 `logs/*.jsonl` 文件。选择 JSONL（JSON Lines）是因为它写入性能高（追加写入）、结构灵活（每行一个完整的 JSON 对象，适应不同阶段的日志结构），且便于通过 grep/jq 等工具进行简单调试。Dashboard 中的 `TraceService` 会读取这些日志文件，根据 Trace ID 聚合 Ingestion 或 Query 的各个阶段耗时与元数据，再通过 Streamlit 进行渲染。

5. **Ingestion 的 Waterfall（瀑布图）是如何实现的？它展示了哪些关键信息？**
   - **参考答案**：Waterfall 图是通过解析 Ingestion Trace 日志中的时间戳（Start/End Time）生成的。它展示了文档处理 Pipeline 中每个步骤（如 Loader, Splitter, Embedder, Store）的起止时间与持续时长。这有助于快速定位性能瓶颈（例如，发现 Embedding 阶段耗时过长），或者发现某个步骤是否被跳过（Latency 为 0 或缺失）。

6. **Query Traces 页面展示了检索链路的哪些细节？**
   - **参考答案**：Query Traces 页面还原了 RAG 检索的全过程：从原始 Query 输入，到 Dense Retrieval（向量检索）和 Sparse Retrieval（关键词检索）的并行执行，再到 Fusion（融合排序）和 Rerank（重排序）的结果。通过可视化，我们可以清晰地看到每一路检索召回了哪些 Chunk，以及 Rerank 前后的分数变化，这对调试检索效果非常有帮助。

7. **如果日志文件非常大（例如 GB 级别），Dashboard 的 TraceService 会有什么性能问题？你有什么优化思路？**
   - **参考答案**：当前实现是全量读取解析，如果日志文件过大，会导致内存飙升和页面加载缓慢。优化思路包括：(1) **分页读取/按需读取**：只读取文件的最后 N 行（类似于 `tail`）；(2) **日志轮转（Log Rotation）**：按日期或大小切割日志文件，Dashboard 只默认加载最新的日志；(3) **索引机制**：在写入日志时同时维护一个轻量级的 TraceID 索引文件，查询时通过索引定位文件位置。

8. **Dashboard 如何触发后端的 Ingestion 任务？是同步还是异步的？**
   - **参考答案**：在 Ingestion 管理页面上传文件后，前端会调用 `IngestionPipeline` 的执行方法。在目前的 Streamlit 实现中，这通常是同步阻塞的，即用户点击“Start Ingestion”后，界面会显示 Spinner 等待直到处理完成。对于生产环境的大文件处理，建议改为异步模式：前端只提交任务到队列，后端 Worker 处理，前端通过轮询状态来更新进度条。

9. **为什么选择 Streamlit 而不是 React/Vue + FastAPI 的前后端分离方案？**
   - **参考答案**：这是基于“开发效率”与“阶段目标”的权衡。在当前阶段（POC/MVP），我们的首要目标是快速构建一个可用的内部管理工具来验证 RAG 流程。Streamlit 允许用纯 Python 代码快速构建数据密集型 UI，极大地降低了开发成本。如果未来系统需要面向外部用户或需要高度定制的交互，我们会考虑迁移到 React + FastAPI 架构，届时后端的 `DocumentManager` 和 Pipeline 逻辑可以直接复用。

10. **Data Browser 页面的分页功能是如何实现的？**
    - **参考答案**：由于底层 ChromaDB 和 BM25 的查询接口支持 `limit` 和 `offset`（或类似切片操作），Data Browser 页面通过前端的分页组件（Page Number Selector）计算出对应的 offset，然后只向后端请求当前页所需的数据。这避免了将所有 Document 加载到前端内存中，保证了在数据量较大时的页面响应速度。

11. **如果后端配置（如 Embedding 模型）在运行时发生了变化，Dashboard 需要重启吗？**
    - **参考答案**：通常建议重启。虽然 Dashboard 有 `ConfigService` 读取配置，但很多核心组件（如 LLM Client, Embedding Function）是在应用启动时初始化的单例。如果运行时修改了 `.env` 或配置文件，为了确保所有组件使用新配置，重启 Dashboard 进程是最安全的方式。不过，我们在 Dashboard 中展示的配置信息是实时读取的，可以用于确认当前生效的配置。

12. **在实现过程中，遇到了什么“多存储后端”带来的挑战？**
    - **参考答案**：主要挑战在于**数据同步与状态一致性**。例如，向 Chroma 写入成功但向 BM25 写入失败时，如何回滚？目前的实现采用了“尽最大努力写入”策略，并记录错误日志。在 `DocumentManager` 中，我们尽量将操作序列化，但在没有分布式事务支持的情况下，确实存在极低概率的不一致风险。未来的改进方向是引入 WAL (Write-Ahead Log) 或使用支持多模态的单一数据库。

13. **如何验证 Dashboard 的功能正常？有自动化测试吗？**
    - **参考答案**：我们实现了冒烟测试脚本（Smoke Test），例如通过 `python scripts/start_dashboard.py` 确保服务能启动。对于 UI 交互，目前主要依赖人工验收（Manual Verification），按照验收清单检查文件上传、搜索、链路追踪图表渲染等功能。对于底层的 Service 和 Manager 类，我们有单元测试（Unit Tests）覆盖其核心逻辑。

14. **Dashboard 是否支持多用户登录和权限控制？**
    - **参考答案**：当前阶段不支持。Streamlit 社区版默认是单用户的（或者说无状态的共享访问）。如果需要权限控制，通常的做法是在 Nginx 层做 Basic Auth，或者使用 Streamlit 的第三方鉴权组件。但在本项目作为内部开发调试工具的定位下，暂未引入复杂的鉴权机制。

15. **Query Traces 中的 "Latency" 数据准确吗？它是如何计算的？**
    - **参考答案**：Latency 是基于应用层打点计算的。我们在代码的关键路径（如 `RetrievalService.retrieve` 的开始和结束处）记录了时间戳。这些时间戳反映了 Python 代码执行的耗时，包含网络 I/O（如调用 OpenAI API）和本地计算时间。虽然它不是内核级的精确剖析，但对于分析 RAG 流程中的性能瓶颈（例如区分是 LLM 慢还是检索慢）已经足够准确。

16. **如果我上传了一张图片，Dashboard 如何展示它？**
    - **参考答案**：`DocumentManager` 支持 ImageStorage。当在 Data Browser 中浏览到类型为 Image 的 Chunk 时，Dashboard 会通过 Chunk 元数据中记录的文件路径（或 URL）加载图片，并使用 `st.image` 组件进行渲染。这要求 Dashboard 进程对存储图片的目录有读取权限。

17. **在开发 Dashboard 时，如何处理依赖项（Dependencies）？**
    - **参考答案**：Dashboard 依赖了 `streamlit`, `pandas` (用于表格展示), `plotly` (用于绘制图表) 等库。这些依赖都被声明在项目的 `pyproject.toml` 或 `requirements.txt` 中。在启动脚本中，我们会检查环境，确保所有必要依赖都已安装，否则会报错提示。

18. **TraceService 中的数据解析逻辑如果出错（例如日志格式损坏）会怎样？**
    - **参考答案**：`TraceService` 在解析日志行时包含 `try-except` 块。如果某一行 JSON 解析失败或字段缺失，该行会被跳过（并记录 Warning），而不会导致整个 Dashboard 崩溃。这是为了保证可观测性工具自身的鲁棒性——即使日志有部分损坏，也能查看到其余正常的数据。
