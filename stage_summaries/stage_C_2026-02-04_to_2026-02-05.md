## 面试问题与答案（阶段 C）

> Updated: 2026-02-05

1. 请你用 2 分钟概括“离线摄取（Ingestion）”在 RAG 系统中的价值：它解决了什么问题，为什么必须先把它打通？
   - 参考答案：离线摄取的核心价值是把“高成本、可变、易失败”的文档预处理从 Query 时延路径里剥离出来，提前把文档变成可检索的稳定产物。阶段 C 里产物至少包含向量库记录（dense embedding）、BM25 索引落盘（`data/db/bm25/<collection>/`）以及图片落盘（`data/images/<collection>/`）。先打通摄取意味着后续检索链路能在“可用的索引与元数据”基础上迭代，而不是一边检索一边补底层数据管道。

2. 阶段 C 的目标是把 PDF→MD→Chunk→Embedding→Upsert 跑通。你会如何向面试官解释这条链路每一步“在做什么”和“为什么要做”？
   - 参考答案：先做完整性检查与增量判断（基于文件 hash）避免重复处理；再把文件加载成统一的文本/中间格式（如 MD）降低后续处理的多样性；然后切分成 chunks，控制上下文粒度与 embedding 成本；接着在 transform/enrichment 层做规则增强与可选的 LLM 增强（可降级）提升后续可检索性；再对 chunk 编码得到 dense 向量，同时统计生成 sparse 信息用于 BM25；最后以稳定的 chunk_id hash 做 upsert 保证幂等，并把 BM25 索引与图片等副产物落盘，形成可复现的索引状态。

3. 你把流程拆成多个阶段（例如完整性检查、加载、切分、增强、编码、写入、落盘索引）。这种分阶段设计的核心收益是什么？最常见的代价是什么？
   - 参考答案：收益是可观测、可替换、可重试：每阶段输入/输出清晰，便于定位瓶颈与失败点，也便于替换某一环（例如 Splitter/Encoder）而不重写全链路；同时能更精细地做降级策略（例如 LLM 增强失败不阻塞主链路）。代价通常是状态与边界变多：需要定义阶段间契约、错误传播与“部分成功”的处理方式，并承担一定的工程复杂度与调试成本。

4. 在摄取链路里，为什么要先做“文件完整性检查（SHA256）/增量跳过”？它在成本、性能、数据一致性上分别带来什么影响？
   - 参考答案：成本上，跳过未变更文件可以显著减少 embedding/LLM 调用与 IO；性能上，避免重复切分/编码让批量摄取更快；一致性上，增量机制结合幂等 upsert 能让“重复执行”更可控，降低重复 chunk、索引漂移的概率。阶段 C 明确把 hash 作为增量判断信号，并将写入端做幂等（chunk_id hash）来收敛最终状态。

5. 如果面试官追问“hash 增量跳过一定可靠吗”，你会列出哪些可能的误判场景？你会如何设计更稳健的增量策略（版本、配置指纹、collection 维度等）？
   - 参考答案：不一定可靠：即使源文件没变，切分参数、transform 规则、caption 策略、encoder 版本变化也会导致“应该重建但被跳过”；反过来，抽取过程非确定（例如 PDF→MD 解析器升级）也会让相同文件产生不同文本。更稳健的策略是把“输入文件 hash + pipeline 版本/配置指纹（splitter 配置、transform 开关、encoder 版本）+ collection 维度”组合成 fingerprint，并记录到清单里，用它作为增量判断与回滚依据。

6. 你如何定义“幂等（Idempotency）”在摄取阶段的含义？为什么 RAG 系统里幂等比很多传统 ETL 更重要？
   - 参考答案：在摄取里幂等意味着同一输入与同一配置重复执行，最终向量库/索引/落盘产物的状态不应产生重复与漂移，或至少能被稳定覆盖更新。RAG 更强调幂等是因为摄取经常涉及重试（网络/LLM/embedding 抖动）、多次回放、分批增量，且“重复 chunk”会直接污染检索结果与成本（召回冗余、rerank 噪声、回答重复）。

7. 在切分（Chunking）上，你会如何解释“切得太大/太小”的典型问题，以及你会用哪些指标或现象来判断 chunk 质量好坏？
   - 参考答案：太大：embedding 成本高、召回粒度粗、回答引用范围过大且容易引入无关内容；太小：语义上下文断裂、需要聚合多个 chunk 才能回答、检索结果碎片化导致答案不连贯。判断质量可看：每文档 chunk 数量分布、召回命中后答案是否容易 grounding、topK 检索结果的重复度、以及在 e2e 测试/人工评估中“找得到/答得对/引用得稳”的表现。

8. 为什么要把 Splitter 设计成可插拔（pluggable）？在面试中你会如何用“文档类型差异/业务场景差异”来说明这个设计是必要的？
   - 参考答案：不同文档（PDF、Markdown、网页、代码、表格）结构差异很大，最优切分策略不可能一刀切；业务场景也不同：有的更看重精确定位（小 chunk），有的更看重上下文（大 chunk + overlap）。可插拔把“策略选择”从“管道编排”里隔离出来，允许在不改主流程的前提下按 collection/类型替换 Splitter，降低长期演进成本。

9. 在 transform/enrichment 这一层，你为什么会引入“规则增强 + 可选 LLM 增强 + 失败降级”？你会如何解释这种工程策略背后的稳定性与成本权衡？
   - 参考答案：规则增强（deterministic）提供稳定底座，例如清洗、标题提取、基础元数据；LLM 增强提升可检索性与可读性（例如摘要、标签、caption），但不稳定且昂贵。把 LLM 作为可选并支持失败降级，可以在“链路可用性”与“质量提升”之间做分层：没有 LLM 也能摄取并产出索引，有 LLM 时再增益质量。

10. 你在摄取链路里如何处理“LLM 不可用/超时/限流”？哪些步骤可以降级，哪些步骤必须失败中止？为什么？
   - 参考答案：可降级的通常是增强类步骤：例如 ImageCaptioner、摘要/标签生成等，失败时用占位/空字段继续推进，避免阻塞主链路。必须失败中止的是主链路不可替代的步骤：比如无法得到可切分的文本内容（Loader 失败）或无法写入核心索引（Upsert 失败且无补偿），因为这会让产物缺失或不一致。阶段 C 的总结明确了“LLM 可选、失败可降级”的策略方向。

11. 为什么要做元数据增强（title/summary/tags 这类）？这些信息在后续检索、过滤、展示、调试里分别可能起什么作用？
   - 参考答案：检索上，元数据可用于过滤（collection、doc_id、类型）、rerank 特征、或作为 Hybrid 的补充信号；展示上，title/summary 提升可读性与可解释性；调试上，tags 与摘要能快速判断 chunk 是否来自正确文档/主题，缩短排障路径；同时元数据还能作为“数据血缘/版本”载体，支持回滚与重建。

12. 阶段 C 里引入图片处理（Image-to-Text / Image Captioning）。你会如何向面试官解释“为什么先做图转文，而不是上多模态向量模型”？其边界与风险是什么？
   - 参考答案：先做图转文的好处是把图片信息落到文本域，复用现有的 text embedding + BM25 管道，工程复杂度低、可快速验证端到端闭环。边界与风险是 caption 质量不稳定，图表/公式/结构化信息可能丢失；此外如果 caption 输入是占位或链接不可用，会导致增强失效但不应阻塞主流程（需要明确降级行为）。

13. 如果要让摄取链路在生产环境可运维，你会记录哪些关键事件/指标（例如每阶段耗时、失败率、跳过率、产物规模）？这些指标分别用来回答什么问题？
   - 参考答案：每阶段耗时/吞吐用于定位瓶颈（IO、切分、编码、写入谁慢）；失败率按阶段拆分用于定位不稳定点（Loader/LLM/Upsert）；跳过率用于评估增量策略收益与误判风险；产物规模（chunk 数、向量条数、BM25 文档数、图片数）用于容量规划与异常检测（突然暴涨/暴跌）；外部调用指标（embedding/LLM 次数、超时、限流）用于成本与稳定性控制。

14. 为什么要在摄取阶段同时准备 Dense 与 Sparse 两条信息（Embedding + BM25 索引）？它们分别擅长解决什么检索问题？
   - 参考答案：Dense embedding 擅长语义相似、同义改写、长尾表达；Sparse（BM25）擅长关键词精确匹配、术语/编号/实体、短 query 与强约束场景。阶段 C 同时落盘 BM25（`data/db/bm25/<collection>/`）与向量写入，为后续 Hybrid Search 提供基础。

15. 你会如何用“混合检索（Hybrid Search）”的动机解释：为什么仅有语义向量或仅有 BM25 都不够？典型坏 case 是什么？
   - 参考答案：仅 dense 时，遇到必须精确匹配的 token（版本号、错误码、专有名词）容易漏召回；仅 BM25 时，遇到强语义改写或跨表述的需求（“如何做增量幂等” vs “避免重复写入”）召回质量差。Hybrid 的动机是把两者的优势叠加，并在 rerank/融合阶段做权重与策略控制，降低单一检索的盲区。

16. 你们把 BM25 索引落盘到本地文件。面试官问“规模上来怎么办”，你会从存储结构、加载方式、查询性能三个角度给出哪些演进路线？
   - 参考答案：存储结构上可以从单机文件扩展到分片目录（按 collection/doc 分片）并引入版本；加载方式上可做 mmap/按需加载与缓存，避免全量加载；查询性能上可以做预热、并行查询与候选裁剪，或演进到专用检索引擎（例如把 BM25/倒排交给成熟服务），同时保留本地模式作为开发/小规模 fallback。

17. 摄取链路里最容易出现“部分成功（partial success）”。你会如何定义事务边界与补偿机制，保证数据最终一致（或至少可恢复）？
   - 参考答案：关键是定义“提交点”：例如 upsert 成功但 BM25 落盘失败时，是否允许存在“向量已更新、BM25 未更新”的短暂不一致；工程上可用 staging 目录 + finalize 原子切换来保证落盘一致性，并记录每次 run 的清单（输入 fingerprint、产物版本）。补偿机制包括：可重跑（幂等 upsert + 可重建 BM25）、可清理（按 collection/doc 清理产物）以及失败时回滚到上一版本索引。

18. 摄取的产物通常包含：向量库记录、BM25 索引、图片文件/映射表。你会如何设计清理、重建、回滚策略，支持快速排障与回归？
   - 参考答案：以 collection/doc_id 作为最小清理粒度，支持“删除某 doc 的所有 chunk 与其索引片段”；重建策略上以源文件 + fingerprint 作为真源，允许只重建 BM25 或只重建向量；回滚策略上保留索引版本目录（至少保留上一个可用版本）并在 finalize 时切换指针；图片落盘同样需要可定位到 doc/collection 的目录结构，支持快速删除与重跑生成。

19. 阶段 C 的测试为什么要同时包含 unit/integration/e2e？你会如何解释它们各自覆盖的风险面，以及如何避免测试强依赖外部服务（LLM/Embedding）？
   - 参考答案：unit 覆盖纯逻辑与边界（例如 hash/幂等/序列化）让问题定位更快；integration 覆盖模块组合与数据流契约，验证 pipeline 的关键路径；e2e 覆盖 CLI 与落盘产物，确保“用户可用”。避免外部依赖通常通过 mock/stub 或可配置的 deterministic encoder/LLM 占位来实现。阶段 C 总结已给出最小回归与 e2e 命令，体现了分层测试思路。

20. 如果让你继续迭代阶段 C，你会优先补齐哪三类能力（例如真实 PDF→MD 解析质量、增量策略版本化、可观测性/trace、并行化/性能优化）？为什么排序是这样的？
   - 参考答案：优先级 1 是提升输入质量与确定性（例如更可靠的 PDF→MD/文本抽取），因为它决定了后续切分与检索上限；优先级 2 是把增量策略做版本化与配置指纹化，避免“文件未变但索引应重建”的误判，保证长期演进可控；优先级 3 是可观测性与性能（阶段耗时、失败重试、并行化），用于把链路从“可跑通”推进到“可运维”。总结里也提示了 Loader/图片处理存在占位实现，这类是继续迭代的直接抓手。
