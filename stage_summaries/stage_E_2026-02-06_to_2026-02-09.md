### 关键实现点（按模块归纳）

- **Stdio Server 主循环**：以 `stdin` 逐行读取 JSON-RPC 请求，输出只写 `stdout`（MCP 消息），日志写 `stderr`，[server.py](../src/mcp_server/server.py)。
- **协议处理与错误规范化**：封装 JSON-RPC 2.0 的 `initialize` / `tools/list` / `tools/call`，并将异常映射为 -32600/-32601/-32602/-32603 错误码，[protocol_handler.py](../src/mcp_server/protocol_handler.py)。
- **Tool 注册与路由**：`ToolSchema` 定义 `name/description/inputSchema`，注册到 `ProtocolHandler`；`tools/call` 通过 name 路由到 handler，[server.py](../src/mcp_server/server.py#L35-L94)。
- **主检索工具 query_knowledge_hub**：调用 `HybridSearch.search()` + `Reranker.rerank()`，再由 `ResponseBuilder` 统一构建 MCP 响应（Markdown + structured citations），[query_knowledge_hub.py](../src/mcp_server/tools/query_knowledge_hub.py)。
- **响应构建与引用**：引用统一由 `CitationGenerator` 生成；无命中时返回友好提示；命中时返回 Markdown 文本与 citations 结构化字段，[response_builder.py](../src/core/response/response_builder.py) / [citation_generator.py](../src/core/response/citation_generator.py)。
- **多模态组装**：当 chunk metadata 含 `image_refs` 时，读取对应图片文件并 base64 编码为 MCP `image` content，最多返回 `max_images` 张，[multimodal_assembler.py](../src/core/response/multimodal_assembler.py)。
- **补充工具**：
  - `list_collections`：扫描 `data/documents/` 的集合目录并返回基础统计，[list_collections.py](../src/mcp_server/tools/list_collections.py)。
  - `get_document_summary`：按 `doc_id` 从向量库后端（jsonl/chroma）读取元数据并返回 title/summary/tags，[get_document_summary.py](../src/mcp_server/tools/get_document_summary.py)。

## 面试问题与答案（阶段 E）

> Updated: 2026-02-09 00:00

1. 你如何向面试官解释 MCP Server 在整个系统里的定位？它和传统 HTTP API 服务有什么本质差异？
   - 参考答案：本阶段把能力以 MCP tools 的形式对外暴露，重点是给 MCP Client（例如 Copilot/Claude Desktop）通过 Stdio Transport + JSON-RPC 2.0 调用。与传统 HTTP API 的差异在于：传输介质是标准输入输出、协议是 JSON-RPC（含 request id、method、params），并且强调“工具调用（tools/list、tools/call）”的能力协商与可发现性，而不是固定的 REST 路由。

2. 为什么要把“协议解析（ProtocolHandler）”和“工具实现（tools/*）”拆开？这样拆分带来什么工程收益？
   - 参考答案：拆分的核心收益是职责清晰与可测试性：协议层只关心 JSON-RPC 合法性、错误码、能力协商与路由；工具层只关心业务逻辑和返回格式。这样单测可以只验证 ProtocolHandler 的协议行为（错误码、通知不返回等），集成测试再验证 stdio server + tools 的端到端行为，降低耦合并减少回归面。

3. 你们在 stdio server 上是怎么保证“stdout 不被日志污染”的？为什么这个约束重要？
   - 参考答案：阶段 E 的约束是：stdout 只输出 MCP 消息（JSON-RPC 响应），日志全部打到 stderr。重要性在于：MCP Client 是按行/按消息解析 stdout 的，如果把日志混入 stdout，会导致协议解析失败、工具调用不稳定，属于接口层的硬性契约。

4. 解释一下 `initialize`、`tools/list`、`tools/call` 三类请求各自的职责与最小实现要求。
   - 参考答案：`initialize` 用于能力协商，返回 serverInfo 与 capabilities（至少包含 tools 能力声明）；`tools/list` 返回已注册工具的 schema（name、description、inputSchema），用于客户端可发现；`tools/call` 根据 name 路由执行具体工具并返回 result。最小实现要求是三者都遵循 JSON-RPC 2.0 的响应结构（jsonrpc、id、result/error）。

5. JSON-RPC 的错误码你是怎么设计/落地的？为什么要区分 -32601 和 -32602？
   - 参考答案：按 JSON-RPC 2.0 约定规范化错误：无效请求用 -32600、未知方法用 -32601、参数错误用 -32602、内部异常用 -32603。区分 -32601/-32602 的价值在于：客户端能明确判断“调用的方法/工具不存在”还是“方法存在但参数不合法”，便于自动重试、参数修复和体验提示。

6. `tools/list` 返回的 schema 为什么重要？如果没有 schema，会造成什么问题？
   - 参考答案：schema 是工具可发现性与可用性的前提：客户端可根据 inputSchema 生成 UI、做参数校验、做智能提示。如果没有 schema，客户端只能“盲调”，容易出现参数不匹配导致 -32602，降低可用性，也不利于后续扩展更多 tools。

7. 你们的工具返回结构（content + structuredContent）想解决什么问题？为什么不只返回 Markdown？
   - 参考答案：content 面向展示（例如 text + image 多模态），structuredContent 面向机器可读与二次处理（例如 citations 列表、collections 列表）。只返回 Markdown 会让引用、doc_id、tags 等信息变成不可可靠解析的纯文本，难以做后续自动化（比如引用展开、来源定位、二次检索）。

8. query_knowledge_hub 的核心数据流是什么？你会如何用一句话描述它的输入与输出？
   - 参考答案：输入是用户 query（可选 top_k、collection），内部走混合检索与可选重排得到 top hits，输出是 MCP tool result：Markdown 文本答案（带引用编号）+ structured citations，并在命中图片引用时附带 image content（base64 + mimeType）。

9. 为什么在 query_knowledge_hub 里要做“无数据时友好提示”？这属于哪类工程化考虑？
   - 参考答案：这是面向用户体验与可运维性的 fail-soft：当向量库/BM25 没有任何数据时，返回明确提示“先 ingest”，避免返回空数组或难以理解的异常。它同时减少客户端误判（例如把空结果当成系统故障）并让排障路径更短。

10. 多模态返回里，为什么选择“base64 直接回传图片内容”？它的优缺点是什么？
   - 参考答案：优点是协议自包含、客户端无需再访问文件系统或额外下载，适合本地 stdio 的封闭通道；缺点是响应体积会增大、编码开销增加，可能影响性能与延迟，因此需要控制数量（例如 max_images）并做好缺失/读取失败的容错。

11. 在多模态组装中，你们如何避免返回过多图片导致响应过大？如果未来要优化，你会怎么做？
   - 参考答案：当前通过上限（max_images）限制图片数量并去重；未来优化方向包括：只返回最相关图片、支持返回缩略图、支持客户端按需二次拉取（例如先返回 image_id/路径，再由 client 触发资源获取），或引入缓存与分片传输策略（需结合 MCP 能力与约束评估）。

12. list_collections 工具在产品视角有什么价值？除了返回集合名，你还会补充什么信息？
   - 参考答案：价值是可发现与可运维：用户能知道当前有哪些知识库集合可用。除了集合名，还可以补充基本统计（文件数、chunk 数、最后摄取时间、索引健康状态），但需要权衡：统计成本、实现复杂度与数据源的可靠性。

13. get_document_summary 按 doc_id 返回摘要/标签，这个工具更适合用于什么交互流程？
   - 参考答案：更适合“检索后回溯”和“结果解释”：当 query 返回了一些 citations，客户端可以基于 doc_id（或由 citations 映射）拉取文档级摘要与标签，展示为侧边栏或 hover 卡片，帮助用户快速理解来源与上下文。

14. 你如何设计工具的参数校验策略？校验放在协议层还是工具层，为什么？
   - 参考答案：协议层负责“params 必须是对象”等通用校验以及错误码规范化；工具层负责业务语义校验（例如 query 非空、top_k > 0、doc_id 非空）。这样既保持协议层通用性，又让工具具备清晰的输入契约与可维护的错误信息。

15. 你会如何验证 MCP Server 的可靠性？阶段 E 的测试策略体现了什么思路？
   - 参考答案：阶段 E 采用“单测 + 集成测试”的组合：单测验证 ProtocolHandler 的 JSON-RPC 行为与边界；集成测试用子进程启动 stdio server，模拟 initialize/tools/list/tools/call 的 roundtrip，并对 stdout/stderr 的约束做断言。思路是把协议契约当成接口测试的核心，避免只测业务函数而遗漏传输与协议层问题。

16. 如果客户端发送了通知（没有 id），你们为什么选择不返回响应？这符合什么规范？
   - 参考答案：JSON-RPC 2.0 规定通知（Notification）不应该有响应；不返回能避免客户端等待不存在的结果，同时也符合协议语义。阶段 E 的协议处理明确了 request id 为 None 时返回 None。

17. 如何避免在 error 响应里泄露堆栈或敏感信息？你会怎么做安全收口？
   - 参考答案：接口层只返回规范化 error（code/message），不把异常堆栈透出到 stdout 的协议响应里；详细日志仅写 stderr 或本地日志文件（后续阶段 F 会做结构化追踪）。安全收口还包括：不在响应体里回显配置秘密、对用户输入做长度限制、对路径类参数做白名单或禁用直接文件访问等。

18. 如果要新增一个 tool（例如删除集合或重建索引），你会遵循什么步骤来保证兼容性与可回归？
   - 参考答案：先定义 tool schema（inputSchema）与输出 shape（content/structuredContent），再在 server 注册与路由，补齐协议层/工具层的参数校验，添加单测验证工具函数行为，最后加集成测试验证 stdio roundtrip。兼容性要点是：不破坏已有 tools/list 输出结构与既有 tool 的 result shape。

19. 你如何看待“工具的稳定输出结构”与“快速迭代”之间的矛盾？你会如何做版本化？
   - 参考答案：对外 tool 的输入输出一旦被客户端依赖，就应尽量稳定；迭代可以通过新增字段（向后兼容）而非修改/删除字段。需要版本化时，可在 initialize 的 serverInfo/version 中体现，并在 structuredContent 中引入 schemaVersion，或以新 tool 名称（v2）并存一段时间，逐步迁移客户端。

20. 如果阶段 F 要引入 TraceContext，你会把 trace 贯穿在 MCP Server 调用链路的哪些位置？为什么？
   - 参考答案：trace 应在请求入口生成并贯穿到工具执行链路：ProtocolHandler/Server 负责创建并管理请求级上下文；tools/call 执行具体工具时传入 trace；核心检索/重排/响应构建阶段记录关键阶段信息（耗时、候选数量、是否 fallback 等）。这样才能把“客户端发起一次工具调用”作为一个可追踪的完整请求，实现后续 dashboard 与回归分析。
