### 关键实现点
- **TraceContext 生命周期管理**: 明确了 Trace 的创建、传递、阶段记录 (`record_stage`) 和最终完成 (`finish`) 的生命周期。
- **非侵入式打点**: 通过 `trace: Optional[TraceContext]` 参数传递上下文，不影响核心业务逻辑。
- **结构化数据存储**: 采用 JSON Lines 格式存储 Trace，便于后续流式读取和分析。
- **进度反馈解耦**: `on_progress` 回调设计使得 UI 层可以订阅后台任务进度，而无需耦合具体实现。

## 面试问题与答案（阶段 F）

> Updated: 2026-02-11 00:00

1. **为什么在 RAG 系统中需要全链路追踪（Tracing）？**
   - **参考答案**：RAG 系统包含检索、排序、生成等多个复杂阶段，且涉及外部模型调用。全链路追踪能帮助我们：1) **定位瓶颈**：明确是检索慢、重排序慢还是 LLM 响应慢；2) **调试质量**：记录每个阶段的输入输出（如 Top-K 结果），便于分析 Bad Case；3) **数据驱动优化**：通过收集真实流量的 Metrics（耗时、Token 数），为系统优化提供依据。本阶段实现的 `TraceContext` 就是为了解决这些问题。

2. **`TraceContext` 是如何设计生命周期的？**
   - **参考答案**：`TraceContext` 采用显式的生命周期管理：1) **初始化**：在请求入口（如 Query 或 Ingestion）创建，生成唯一 `trace_id`；2) **传递**：通过函数参数（如 `trace: Optional[TraceContext]`）在各层间透传；3) **记录阶段**：各业务组件调用 `record_stage()` 记录阶段名、耗时和元数据；4) **结束与落盘**：流程结束时调用 `finish()` 计算总耗时，并通过 `JsonlLogger` 写入日志文件。

3. **为什么选择 JSON Lines (`.jsonl`) 作为日志格式？**
   - **参考答案**：相比于传统文本日志或单个大 JSON 文件，JSON Lines 有以下优势：1) **追加写入高效**：每行一个完整的 JSON 对象，无需解析整个文件即可追加；2) **流式处理友好**：读取时可逐行解析，内存占用低，适合大数据量分析；3) **结构化强**：保留了 JSON 的结构化特性，方便 Dashboard 前端或数据分析工具（如 Pandas/Elasticsearch）直接摄入。

4. **如何在不修改现有业务逻辑核心的前提下注入 Trace？**
   - **参考答案**：采用了**参数注入**和**可选类型**的策略。在现有函数签名中增加 `trace: Optional[TraceContext] = None` 参数。业务逻辑内部通过 `if trace: trace.record_stage(...)` 进行打点。这种方式是非侵入式的，且兼容旧的调用方式（不传 trace 时默认为 None，不执行打点逻辑，开销极小）。

5. **`IngestionPipeline` 的进度回调 (`on_progress`) 与 Trace 有什么区别？**
   - **参考答案**：两者关注点不同：**Trace** 关注的是**事后分析**和**全链路性能/质量**（记录耗时、输入输出），主要供开发者和运维使用；**Progress Callback** 关注的是**实时状态反馈**（当前处理到第几步、百分比），主要供前端 UI 展示给最终用户。两者可以共存，Trace 记录详细日志，Callback 触发轻量级 UI 更新。

6. **在 `TraceContext` 序列化时，如何处理非 JSON 可序列化的对象（如自定义对象或 Dataclass）？**
   - **参考答案**：在 `TraceContext.to_dict()` 或 JSON 序列化器中需要做特殊处理。通常做法是检测对象类型，如果是 Dataclass 则转为 dict，如果是其他不可序列化对象（如 Set、Complex Object），则降级为字符串表示（`str(obj)`）或提取关键 ID，防止序列化抛出异常导致 Trace 丢失。

7. **如果 Trace 系统本身的写入出现异常，如何避免影响主业务流程？**
   - **参考答案**：Trace 系统应遵循**Fail-Safe（故障静默）**原则。在 `record_stage` 或 `logger.write_trace` 内部应捕获所有异常（`try-except Exception`），并打印错误日志（如 stderr），但绝不能抛出异常中断主业务流程。Trace 是辅助功能，不能因为辅助功能的故障导致核心业务不可用。

8. **如何保证 `trace_id` 的全局唯一性？**
   - **参考答案**：通常使用 UUID (Version 4) 生成 `trace_id`。UUID v4 基于随机数生成，碰撞概率极低，足以满足单机甚至分布式环境下的唯一性需求。在 `TraceContext` 初始化时自动生成：`self.trace_id = str(uuid.uuid4())`。

9. **在并发环境下（如多线程处理 Ingestion），Trace 如何保证数据的正确性？**
   - **参考答案**：如果是多线程环境，需要注意 `TraceContext` 的线程安全性。最简单的做法是**每个请求/线程独占一个 TraceContext 实例**（Thread-Local 或参数传递），避免多线程共享修改同一个 Trace 实例。在本项目的 Ingestion Pipeline 中，每个文件处理任务通常是独立的，或者通过参数显式传递 Trace 实例，从而规避了并发冲突。

10. **如何衡量 Trace 系统引入的性能开销？**
    - **参考答案**：可以通过基准测试（Benchmark）对比开启和关闭 Trace 时的系统吞吐量（RPS）和延迟（Latency）。开销主要来自：1) 时间获取（系统调用）；2) 对象创建与内存占用；3) 日志序列化与磁盘 IO。设计时应尽量减少大对象的深拷贝，IO 操作最好异步化（尽管本项目目前是同步写入，未来可优化为异步队列写入）。

11. **`record_stage` 方法中记录 `inputs` 和 `outputs` 有什么潜在风险？**
    - **参考答案**：主要风险是**数据量过大**和**敏感信息泄露**。如果 input/output 包含长文本（如整个文档内容）或大向量数组，会导致日志文件急剧膨胀，IO 成为瓶颈。策略是：1) **截断**：只记录文本前 N 个字符；2) **摘要**：只记录列表长度或数据的 Hash/ID；3) **脱敏**：过滤掉敏感字段。

12. **如何设计 Trace 的采样策略（Sampling）？**
    - **参考答案**：在流量很高时，全量记录 Trace 会带来巨大的存储和性能压力。可以引入采样机制：1) **概率采样**：如只记录 1% 的请求；2) **特征采样**：只记录耗时超过阈值（Slow Query）或发生错误的请求；3) **动态采样**：根据系统负载动态调整采样率。当前阶段虽未实现，但在大规模生产环境中是必须考虑的。

13. **Ingestion 阶段的 Trace 和 Query 阶段的 Trace 有什么结构上的不同？**
    - **参考答案**：**Query Trace** 通常是**短链路、低延迟**的，关注检索召回率、重排序分数和 LLM 生成质量，结构偏向于“请求-响应”树状结构；**Ingestion Trace** 往往是**长耗时、批处理**的，关注分块数量、Embedding 维度、向量库写入成功率，结构偏向于“流水线”线性结构。但两者都可以复用统一的 `TraceContext` 数据模型（Stages + Metrics）。

14. **Dashboard 如何利用这些 JSONL 日志进行可视化？**
    - **参考答案**：Dashboard（阶段 G）可以：1) **读取**：解析 JSONL 文件；2) **聚合**：计算平均耗时（P95/P99）、总请求数、错误率；3) **展示**：绘制耗时趋势图、Stage 耗时占比饼图（甘特图）、最近 Trace 列表。通过 `trace_id` 还可以下钻查看单次请求的详细瀑布图。

15. **如果未来要支持分布式追踪（Distributed Tracing），目前的 `TraceContext` 需要做什么改造？**
    - **参考答案**：目前的 `TraceContext` 是进程内的。支持分布式追踪（如 OpenTelemetry 标准）需要：1) **Context Propagation**：支持从 HTTP Header 或 RPC Metadata 中提取和注入 `trace_id` 和 `span_id`；2) **Span 结构**：将 `stages` 升级为具有父子关系的 `Span`；3) **统一上报**：不再直接写本地文件，而是发送给 Collector（如 Jaeger/Zipkin）。但当前的设计思想（ID 传递、阶段记录）是通用的。

16. **为什么在 `IngestionPipeline` 中同时需要 `TraceContext` 和 `logger`？**
    - **参考答案**：**Logger**（应用日志，INFO/ERROR）用于记录系统运行状态、错误堆栈，是给**运维**看“系统是否健康”的；**TraceContext**（业务追踪）用于记录业务流程的数据流转、耗时分析，是给**开发/算法**看“效果好不好、慢在哪里”的。两者互补，不可互相替代。Trace 数据最终也可以通过 Logger 落盘。

17. **在实现 `on_progress` 回调时，如何处理总任务量未知的情况？**
    - **参考答案**：在流式处理或大文件读取初期，总大小（total）可能未知。做法是：1) 尽可能估算（如文件字节大小）；2) 如果完全无法预估，`total` 传 `None` 或 `-1`，前端 UI 展示为“加载中...”的无限进度条（Indeterminate Progress Bar），而不是百分比进度条。

18. **如何验证 Trace 系统记录的时间戳是准确的？**
    - **参考答案**：可以使用 `time.perf_counter()` 或 `time.monotonic()` 获取高精度单调时间，避免受系统时钟回调（NTP）影响。验证方法是编写单元测试，模拟延时（`time.sleep`），断言记录的 `elapsed_ms` 与 sleep 时间在允许误差范围内（如 ±10ms）。
